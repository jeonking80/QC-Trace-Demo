# 저장 프로시저 설명 연습: usp_ApplyInspection

면접에서 "이 저장 프로시저가 무엇을 하는지 설명해 보라"는 질문에 답하기 위한 정리입니다(PLAN 10장). 원문은 [`src/QcTrace.Web/Data/Sql/V3/001_usp_ApplyInspection.sql`](../src/QcTrace.Web/Data/Sql/V3/001_usp_ApplyInspection.sql)입니다.

## 한 문장 요약

검사 실적 한 건을 받아, **같은 요청이면 저장된 응답만 돌려주고**, 아니면 **LOT 행을 잠근 채** 규칙을 검사한 뒤 검사 행·원장 행·현재 수량을 **한 트랜잭션으로** 바꾸고, 응답을 요청 키와 함께 저장합니다.

## 순서대로 설명하기

| 순서 | 코드에서 찾을 곳 | 설명할 말 |
| --- | --- | --- |
| 1 | `SET XACT_ABORT ON` | 중간에 오류가 나면 트랜잭션 전체를 되돌립니다. 반쯤 반영된 수량이 남지 않습니다. |
| 2 | 입력 검사 `THROW 50400`, `52004` | 수량 0 이하, 판정 값, 사유(R4)처럼 DB를 보지 않아도 되는 검사를 트랜잭션 전에 합니다. |
| 3 | `@BodyHash = HASHBYTES('SHA2_256', ...)` | 요청 본문(LOT, 수량, 판정, 측정값 등)의 지문입니다. 같은 키로 다른 내용이 오는 것을 가려냅니다. |
| 4 | `QcRequests WITH (UPDLOCK, HOLDLOCK)` | **멱등 처리(R6)**. 키가 이미 있으면 본문 지문을 비교해, 같으면 저장된 응답을 `Replayed = 1`로 돌려주고 끝냅니다. 다르면 50409. HOLDLOCK은 같은 키가 동시에 두 번 와도 둘째가 첫째의 커밋을 기다리게 합니다. |
| 5 | `Lots WITH (UPDLOCK, ROWLOCK)` | **LOT 단위 직렬화(R8)**. 같은 LOT에 대한 다른 검사·승인·출하는 이 트랜잭션이 끝날 때까지 기다립니다. 다른 LOT은 막지 않습니다. |
| 6 | `THROW 52012` | 검사 의뢰 전 LOT은 검사하지 않습니다. |
| 7 | `@Measured`, `THROW 52014 / 52015` | **R11**. 합격이면 모든 검사 항목이 측정돼 있고 규격(`InspectionItems`의 하한·상한) 안이어야 합니다. 규격은 요청이 아니라 DB 값을 씁니다. |
| 8 | `@Applied`, `@Overage` | **부분 검사(R2)와 초과분(R9)**. 미검사 잔량만큼만 판정 수량으로 옮기고, 넘는 분량은 버리지 않고 보류로 기록합니다. |
| 9 | `INSERT INTO dbo.Inspections`, `@Ledger` → `INSERT INTO dbo.Ledger` | **이력 추가(R3·R10)**. 검사 행과 원장 행(작업자·시각·사유·출처 행)을 새로 넣습니다. 이 테이블들은 트리거가 UPDATE·DELETE를 막습니다. |
| 10 | 정정 분기 `THROW 52011` | 정정은 원 행을 고치지 않고 원 행을 가리키는 새 행을 넣습니다. 원 검사보다 많이, 또는 이미 출하 승인된 합격분을 빼내는 정정은 거절합니다. |
| 11 | `UPDATE LotQuantities`, `usp_RefreshLotStatus` | 현재 수량과 LOT 상태를 원장과 같은 값으로 맞춥니다. 대사 화면과 독립 대조 앱이 이 둘이 같은지 확인합니다. |
| 12 | `INSERT INTO dbo.QcRequests` → `COMMIT` | 응답 JSON을 요청 키와 함께 저장하고 커밋합니다. 같은 키 재전송은 4번에서 이 응답을 그대로 받습니다. |

## 자주 나올 질문

- **왜 앱 코드가 아니라 SP에서 하나요?** 수량을 바꾸는 길을 하나로 만들기 위해서입니다. 앱 계정은 수량·이력 테이블에 직접 쓰기 권한이 없고(DENY, 오류 229) SP 실행 권한만 있습니다. 화면·API·다른 도구 어디서 들어와도 같은 규칙을 거칩니다.
- **UPDLOCK 대신 낙관적 잠금은?** `Lots.RowVersion`도 있지만, 같은 LOT에 동시 요청이 몰릴 때 재시도 없이 순서대로 처리하려고 SP 안에서는 UPDLOCK을 씁니다. 동시 20건 테스트(R8)로 최종 수량이 맞는 것을 확인했습니다.
- **멱등 키는 누가 만드나요?** 화면은 폼을 그릴 때마다 새 키를 넣고, API는 `Idempotency-Key` 헤더로 받습니다. 새로고침·더블클릭·네트워크 재시도에도 한 번만 반영됩니다.
- **직접 짤 수 있나요?** 직접 처음부터 작성하지는 않았습니다. AI가 작성한 코드를 규칙 표와 테스트로 검증했고, 위 동작(잠금, 멱등 키, 트랜잭션)은 설명하고 고칠 수 있습니다.
