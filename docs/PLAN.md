# QC Trace 기획서 · 제조 LOT 검사·출하 이력 관리

Oct 30, 2026 · 전우석

## 1. 목적과 배경

제조업 사내 운영 시스템에서 흔한 .NET·MS-SQL 환경으로 검사·출하 이력 관리 시스템을 설계하고, 실제 동작하는 데모로 만드는 것이 이 프로젝트의 목적입니다. 진행 방식은 업무 규칙 정의 → AI 구현 → 테스트·독립 대조로 결과 확인입니다.

| 영역 | 데모로 보여줄 것 |
| --- | --- |
| .NET | ASP.NET Core 웹 앱 전체 구현 |
| MS-SQL | 스키마 설계, 저장 프로시저, 트리거, 뷰, 마이그레이션 |
| AI 활용 개발 | Claude Code 작업 단위와 검증 기록 공개 |
| 운영 자동화 | 일일 보고서 자동 생성, 지연 알림 |
| HTML / JavaScript | 프레임워크 없는 HTML·JS 대시보드 1개 |
| UI/UX | 현장 작업자 화면과 관리자 화면 분리 |

## 2. 가상 시나리오와 데모 범위

데모 이름은 **QC Trace**, 주제는 **제조 LOT의 검사·출하 이력 관리**입니다. 가상의 압력 용기 제조사가 생산한 LOT을 검사하고, 합격품만 출하 승인하며, 모든 판정과 수량 변경을 이력으로 남깁니다. 특정 회사의 실제 공정을 반영하지 않도록 품목·공정·검사 항목은 모두 가상 데이터로 만듭니다.

**업무 흐름**

1. 생산 LOT 등록: 품목, 수량, 생산일, 작업반
2. 검사 의뢰: LOT을 검사 대기로 전환
3. 검사 실적 입력: 항목별 측정값, 합격·불합격·보류 판정, 부분 검사 가능
4. 불합격 처리: 재검사 요청 또는 폐기, 사유 필수
5. 출하 승인: 검사자 본인은 승인 불가, 다른 승인권자가 처리
6. 출하 실적: 출하 수량 확정, 재고 차감, 이력 확정

**포함 범위**

- 기준정보: 품목, 검사 항목(규격·허용 오차), 사용자·역할
- LOT·검사·출하 업무 화면
- 이력 원장: 수량 변경과 판정 변경을 지우지 않고 추가 기록
- 운영 대시보드: 검사 대기 건수, 지연 LOT, 불합격률, 당일 출하
- 자동화: 일일 검사·출하 보고서 자동 생성(엑셀), 검사 지연 LOT 알림
- 관리자 기능: 사용자·역할 관리, 기준정보 CSV 업로드

**제외 범위**

- 실제 계측 장비 연동, 바코드 스캐너 연동
- ERP·MES 연계
- 다국어, 모바일 앱
- 인증 서버 분리(세션 기반 로그인만)

## 3. 핵심 업무 규칙

규칙은 모두 서버에서 검사합니다. 화면에서 막아도 API로 직접 호출하면 같은 결과가 나와야 하고, 각 규칙은 테스트 1개 이상과 짝을 이룹니다.

| 번호 | 규칙 | 이유 | 검증 방법 |
| --- | --- | --- | --- |
| R1 | 검사 완료 전 LOT은 출하 가능 수량에 포함하지 않는다 | 검사 대기 물량을 출하하면 안 됨 | 검사 전 출하 요청 → 거절 |
| R2 | 부분 검사를 허용하고, 합격·불합격·보류·미검사 수량을 각각 유지한다 | 한 LOT을 여러 번에 나눠 검사하는 현장 | 100개 중 60개 검사 후 수량 합이 100인지 |
| R3 | 판정과 수량 변경은 덮어쓰지 않고 이력에 추가한다 | 품질 이력 추적 | 정정 후 원 기록이 남아 있는지 |
| R4 | 불합격 처리는 사유가 없으면 저장하지 않는다 | 원인 분석 근거 | 사유 없는 요청 → 거절 |
| R5 | 검사자 본인은 자기 LOT의 출하를 승인할 수 없다 | 독립 승인 | 본인 승인 요청 → 거절, 타인 승인 → 성공 |
| R6 | 같은 요청 키로 재전송된 실적은 한 번만 반영한다 | 네트워크 끊김 후 재시도 | 같은 키 2회 전송 → 수량 1회 반영 |
| R7 | 출하 수량은 승인된 합격 수량을 넘을 수 없다 | 재고 음수 방지 | 초과 출하 요청 → 거절 |
| R8 | 동시 요청은 LOT 단위로 직렬화한다 | 동시 입력으로 인한 수량 오류 방지 | 동시 요청 테스트, 최종 수량 일치 |
| R9 | 생산 수량보다 많이 검사 등록된 경우 초과분은 보류로 기록하고 삭제하지 않는다 | 실물 보존 | 과입력 요청 → 보류 수량 생성 |
| R10 | 모든 기록에 작업자·시각·사유를 남긴다 | 감사 추적 | 원장 조회에 세 항목이 모두 있는지 |
| R11 | 합격은 모든 검사 항목을 측정하고 측정값이 모두 규격(하한\~상한) 안이어야 저장한다. 불합격·보류는 저장한다 | 화면 자동 판정을 거치지 않은 합격 입력 방지 | 규격 밖 또는 미측정 항목 + 합격 → 거절, 같은 값 + 불합격 → 성공 |

R11은 2026-11-01 단위 6 검증에서 나온 문제(서버가 규격 밖 측정값의 합격을 받음)를 사용자가 "합격 거절"로 결정해 새 번호로 추가했습니다. 규격은 요청에 담긴 값이 아니라 `InspectionItems`의 하한·상한을 쓰고, 경계값(하한·상한과 같은 값)은 규격 안입니다. 이어서 사용자 결정으로 합격은 그 품목의 검사 항목 전부를 측정해야 저장됩니다. 측정값 생략·빈 값·일부 누락은 합격으로 받지 않고, 정정으로 합격으로 바꿀 때도 새 측정값 전체가 필요합니다. 불합격·보류는 미측정 항목을 허용합니다. 검사 항목이 없는 품목은 측정값 없이 합격할 수 있습니다. 숫자가 아닌 값, 그 품목의 검사 항목이 아닌 값은 입력 오류로 거절합니다. 이미 적재된 시드 기록에는 소급 적용하지 않습니다.

**불량 유형과 폐기 권한** (2026-11-01 사용자 결정)

- 불합격·보류는 불량 유형 목록(`DefectCodes`)에서 고릅니다. 목록에 없으면 "기타"를 고르고 사유를 직접 씁니다(서버가 기타 + 사유 없음을 거절). 다른 유형은 유형 이름이 사유가 되고, 쓴 설명은 "유형 - 설명"으로 붙습니다. 관리자가 기준정보에서 유형을 추가·사용 중지하고 유형별 수량(최근 30일)을 봅니다. 이전 자유 입력 기록은 추가 전용이라 고치지 않고 "유형 없음"으로 집계합니다. 화면은 유형 선택을 강제하고, API는 기존처럼 사유만으로도 받습니다.
- 폐기는 관리자만 합니다(서버가 역할 검사). 검사자는 불합격을 재검사로 되돌리는 것만 하고, 관리자는 "불합격 폐기" 화면에서 사유를 보고 폐기합니다.
- 앱 안 비밀번호 변경 화면은 만들지 않습니다(사용자 결정).

**검사 일정 협의** (2026-11-01 사용자 요청·결정)

수량을 바꾸지 않는 일정 약속도 서버(저장 프로시저)가 검사하고, 기록은 `ScheduleEvents`에 추가만 합니다.

1. 생산 담당이 검사를 의뢰할 때 보통/긴급과 희망 완료 기한(선택)을 고릅니다. 긴급은 사유가 필수이고, 기한은 지금 이후여야 합니다.
2. 검사자 목록은 긴급 → 기한 빠른 순 → 의뢰 오래된 순으로 보이고, "D-1"·"2시간 초과"처럼 남은 시간을 표시합니다.
3. 검사자는 미검사가 남은 LOT(부분 검사 포함)에 "나머지는 언제까지"라는 완료 예정 시각과 사유(필수)를 회신합니다. 확인·결정을 기다리는 회신이 있으면 새로 보낼 수 없습니다.
4. 생산 담당이 수락하면 그 시각이 검사 기한이 됩니다. 거절(사유 필수)하면 바로 결정권자에게 넘어갑니다.
5. 결정권자는 관리자와 승인권자 둘 다이고, 어느 쪽이든 최종 기한(사유 필수)을 정할 수 있습니다. 대시보드 조치 목록에 "일정 결정 필요"로 올라옵니다. 결정권자가 한 번 정한 기한은, 검사자가 새로 회신하고 생산 담당이 수락해도 바로 바뀌지 않고 결정권자 확인을 다시 거칩니다(2026-11-01 사용자 결정).
6. 검사 지연은 기한이 있으면 그 기한, 없으면 의뢰 후 48시간이 기준입니다. 지연 알림(`DelayAlerts`)은 지금처럼 LOT당 처음 한 번만 기록하므로, 한 번 알림이 남은 LOT은 기한이 바뀌어 다시 넘겨도 새로 기록하지 않습니다(대시보드·검사자 목록에는 현재 기한 기준으로 계속 지연으로 보입니다).

**수량 지표** (LOT 단위)

- 생산 수량 = 미검사 + 합격 + 불합격 + 보류 + 폐기
- 출하 가능 = 합격 − 출하 완료 − 출하 예약
- 이 등식이 깨지면 대사 화면에 불일치로 표시합니다.
- 생산 수량을 넘겨 검사된 초과분(R9)은 보류에 더해지므로 "생산 = 미검사 + 합격 + 불합격 + 보류" 등식(폐기 포함)이 초과분만큼 어긋납니다. 이 경우는 실제 불일치와 구분해 대사 화면에 '초과 보류'로 따로 표시합니다.

## 4. 화면 구성

현장 작업자 화면과 관리자 화면을 분리합니다. 작업자 화면은 지금 할 일과 남은 수량을 먼저 보여주고, 관리자 화면은 지연과 불일치를 먼저 보여줍니다.

| 화면 | 사용자 | 핵심 요소 | 구현 방식 |
| --- | --- | --- | --- |
| 로그인 | 전체 | 아이디·비밀번호, 역할별 진입 화면 분기 | Razor Pages |
| 운영 대시보드 | 관리자 | 검사 대기·지연 LOT·불합격률·불합격 처리(대기·오늘 폐기·재검사)·당일 출하(카드를 누르면 해당 LOT 목록), 조치 목록(일정 결정 필요 포함), 지표 설명 | 순수 HTML·JavaScript + fetch API |
| LOT 목록·등록 | 생산 담당 | 품목·수량·생산일 입력, 상태별 필터, 검사 의뢰(보통/긴급·희망 기한), 검사자 일정 회신 수락/거절 | Razor Pages |
| 검사 입력 | 검사자 | 항목별 측정값, 자동 판정, 부분 검사 잔량 표시, 불합격·보류는 불량 유형 선택(기타는 직접 입력). 목록은 긴급·기한 순, 남은 미검사의 완료 예정 시각·사유 회신 | Razor Pages + JS 입력 검증 |
| 불합격 처리 | 검사자 | 재검사 요청, 사유 필수 (폐기는 관리자) | Razor Pages |
| 불합격 폐기 | 관리자 | 불합격 남은 LOT과 사유, 폐기 수량·사유 | Razor Pages |
| 불량 유형 | 관리자 | 유형 추가·사용 중지, 유형별 불량 수량(최근 30일) | Razor Pages |
| 출하 승인 | 승인권자 | 본인 LOT은 버튼 비활성화 + 안내 문구 | Razor Pages |
| 출하 실적 | 출하 담당 | 승인 수량 내 출하, 초과 시 거절 메시지 | Razor Pages |
| 일정 결정 | 관리자·승인권자 | 생산 담당이 거절한 검사 일정의 최종 기한·사유 입력, 기한 초과 LOT, 최근 일정 협의 | Razor Pages |
| 이력 원장 | 관리자 | LOT·작업자·기간 필터, 한 작업을 한 줄·한글로 표시(원장 행 그대로 보기 전환), LOT을 고르면 오래된 순, CSV 내려받기 | Razor Pages |
| LOT 조회·상세 | 역할이 있는 전체 | LOT 번호·품목 검색, 상태 필터. 상세: 수량, 다음 할 일과 담당 역할, 검사 사유·측정값·검사자, 불합격 처리, 승인·출하, 전체 이력. 모든 화면의 LOT 번호가 상세로 연결 | Razor Pages |
| 재고 대사 | 관리자 | LOT별 수량 등식 확인, 불일치 강조 | Razor Pages |
| 기준정보 | 관리자 | 품목·검사 항목·사용자 관리, CSV 업로드 | Razor Pages |
| 보고서·알림 | 관리자 | 검사 지연 알림(열린 것·해소된 것), 일일 엑셀 보고서 목록·내려받기·다시 만들기 | Razor Pages |

대시보드만 프레임워크 없이 만드는 이유는 React 같은 프레임워크 없이 HTML·JavaScript만으로 동작하는 화면을 보여주기 위해서입니다. 나머지는 .NET 기본 스택인 Razor Pages로 통일해 유지보수 환경과 맞춥니다.

## 5. 기술 구성

사내 시스템 환경에 맞춰 .NET과 MS-SQL을 중심에 두고, 나머지는 가장 보편적인 선택으로 고정합니다. 계층마다 선택 이유를 한 줄로 적습니다.

| 계층 | 선택 | 이유 |
| --- | --- | --- |
| 런타임 | .NET 8 LTS, C# | 장기 지원 버전, 사내 시스템 유지보수에 적합 |
| 웹 | ASP.NET Core Razor Pages + Minimal API | 화면과 API를 한 프로젝트에서, 과한 구조 없이 |
| DB | SQL Server 2022 (Docker, Developer Edition) | 사내 시스템에서 흔한 MS-SQL, 로컬에서 무료 실행 |
| DB 접근 | EF Core (조회·CRUD) + 저장 프로시저 (수량 변경) | 수량 변경은 SP 안에서 트랜잭션·잠금 처리, MS-SQL 역량 표시 |
| 마이그레이션 | EF Core Migrations + 수작업 SQL 스크립트 | 스키마 이력 관리 |
| 인증 | ASP.NET Core Identity (쿠키 세션) | 기본 제공, 역할 기반 권한 |
| 프론트 | Razor + 순수 JS, 대시보드는 fetch API | 의존성 최소화 |
| 보고서 | ClosedXML로 엑셀 생성, Hosted Service로 매일 실행 | 운영 자동화 요건 |
| 테스트 | xUnit (단위·통합), Testcontainers (실제 SQL Server), Playwright (E2E) | 결과 검증 |
| 검증 실행 | 로컬 Docker | GitHub Actions는 쓰지 않음(2026-11-01 사용자 결정) |
| 배포 | Docker Compose (앱 + SQL Server) | 한 명령으로 재현 |

**MS-SQL에서 보여줄 것**

- 저장 프로시저 `usp_RegisterLot`, `usp_RequestInspection`, `usp_ApplyInspection`, `usp_DisposeFailed`, `usp_ApproveShipment`, `usp_ShipLot`: 트랜잭션, `UPDLOCK` 행 잠금, 멱등 키 검사
- 역할 변경 `usp_SetUserRoles`: 관리자만, 사유 필수, 바뀐 역할마다 `RoleChanges`에 기록
- 재고 대사 뷰 `vw_LotReconciliation`: 현재 수량 ↔ 원장 합, 생산 등식, R9 초과 보류를 DB에서 판정
- 유니크 제약 `(RequestKey)`로 중복 반영 차단
- 원장 테이블은 INSERT만 허용, UPDATE·DELETE 트리거로 거부
- 조회 인덱스: LOT 상태별, 기간별 원장 조회
- 일일 집계 뷰 `vw_DailyQcSummary`

**멱등 처리 방식**

요청 키 + 요청 본문 해시를 `QcRequests` 테이블에 저장합니다. 같은 키가 오면 저장된 결과를 돌려주고, 키는 같은데 본문이 다르면 충돌로 거절합니다. WMS Lite의 `executeWorkflowInTransaction`과 같은 구조를 MS-SQL 저장 프로시저로 옮기는 것이 목표입니다.

## 6. 데이터 모델

테이블 9개로 시작합니다(단위 7에서 역할 변경 이력 `RoleChanges`를 더해 10개). 현재 상태를 담는 테이블과 이력만 쌓는 테이블을 분리하고, 수량은 항상 이력에서 다시 계산할 수 있어야 합니다.

| 테이블 | 역할 | 주요 열 |
| --- | --- | --- |
| Items | 품목 기준정보 | ItemCode, Name, Spec, IsActive |
| InspectionItems | 품목별 검사 항목 | ItemId, Name, Lower, Upper, Unit |
| Users / Roles | 사용자·역할 (Identity) | UserName, Role (생산·검사·승인·출하·관리자) |
| Lots | 생산 LOT 현재 상태 | LotNo, ItemId, ProducedQty, Status, InspectionRequestedAt, Priority, PriorityReason, DueAt, ScheduleState, ProposedDueAt, RowVersion |
| LotQuantities | LOT별 수량 지표 | LotId, Uninspected, Passed, Failed, Held, Scrapped, Shipped, Reserved |
| Inspections | 검사 실적 (추가만) | LotId, InspectorId, Qty, Verdict, MeasuredJson, Reason, DefectCodeId, CorrectsInspectionId, CreatedAt |
| ShipmentApprovals | 출하 승인 (추가만) | LotId, ApproverId, ApprovedQty, Decision, Reason, CreatedAt |
| Shipments | 출하 실적 (추가만) | LotId, ShipperId, Qty, Destination, CreatedAt |
| Ledger | 불변 원장 | LotId, Kind, DeltaField, Delta, ActorId, Reason, SourceTable, SourceId, CreatedAt |
| QcRequests | 멱등 요청 저장 | RequestKey (unique), Operation, BodyHash, ResponseJson, CreatedAt |
| RoleChanges | 역할 변경 이력 (추가만) | UserId, RoleName, Change(Add·Remove), ActorId, Reason, CreatedAt |
| DelayAlerts | 검사 지연 알림 기록 (추가만, LOT당 1건) | LotId (unique), InspectionRequestedAt, UninspectedAtDetection, DetectedAt |
| DefectCodes | 불량 유형 기준정보 | Code (unique), Name, IsActive, SortOrder |
| ScheduleEvents | 검사 일정 협의 기록 (추가만, 수량 원장과 별도) | LotId, Kind(Request·Propose·Accept·Reject·Decide), Priority, DueAt, Reason, ActorId, CreatedAt |

**설계 원칙**

- `LotQuantities`는 빠른 조회용이고, `Ledger`의 합과 항상 일치해야 합니다. 대사 화면은 이 둘을 비교합니다.
- `Inspections`·`ShipmentApprovals`·`Shipments`·`Ledger`는 UPDATE·DELETE를 트리거로 거부합니다. 정정은 새 행 + 원 행 참조로 기록합니다.
- `Lots.RowVersion`으로 낙관적 잠금, 저장 프로시저 안에서는 `UPDLOCK`으로 LOT 행 잠금을 겹쳐 씁니다.
- 시각은 UTC로 저장하고 화면에서 한국 시간으로 표시합니다.
- `Lots.InspectionRequestedAt`은 검사 의뢰 시각입니다. 검사 지연(48시간 초과) 판단의 기준입니다.
- `Inspections.CorrectsInspectionId`는 정정 행이 가리키는 원래 검사 행입니다. 원 행은 그대로 남습니다.
- `QcRequests.Operation`은 요청 종류(등록·의뢰·검사·불합격 처리·승인·출하)입니다. 같은 키가 다른 작업에 쓰였는지 구분합니다.
- 출하 승인은 `Reserved`(출하 예약)를 늘리고, 출하는 `Reserved`를 줄인 만큼 `Shipped`를 늘립니다. 그래서 출하 가능 = 합격 − 출하 완료 − 출하 예약이 승인 전후 모두 성립합니다.
- LOT은 등록(`Registered`) 상태로 만들어지고, 생산 담당이 검사를 의뢰하면 `Waiting`이 되어 `InspectionRequestedAt`이 기록됩니다. 검사는 의뢰된 LOT만 받습니다.
- 불합격 처리는 불합격 수량을 재검사(→ 미검사) 또는 폐기(→ `Scrapped`)로 옮기고, 둘 다 원장에 행을 남깁니다.
- 역할은 R5(독립 승인)의 근거라서 바꿀 때마다 `RoleChanges`에 누가·언제·무엇을·왜를 남깁니다(2026-11-01 사용자 결정). 앱 계정은 `UserRoles`·`RoleChanges`에 직접 쓰지 못하고 `usp_SetUserRoles`로만 바꿉니다.
- 자동화(Hosted Service `QcAutomation`)는 1분마다 깨어나 검사 지연 LOT을 처음 발견한 시각을 `DelayAlerts`에 남기고, 한국 시간 08:00(`Reports:RunAtKst`)이 지나면 전날 보고서 `qc-daily-yyyyMMdd.xlsx`를 `Reports:Path`(compose 볼륨 `reports`)에 만듭니다. 파일이 이미 있으면 다시 만들지 않고, 08:00에 앱이 꺼져 있었으면 다음에 켜질 때 만듭니다. 보고서 시트: 요약(기준일 실적은 `vw_DailyQcSummary`, 대기·지연·대사는 생성 시점), 검사 실적, 승인·출하, 검사 지연, 재고 대사(정상 제외).
- 대사 화면의 R9 초과 보류 수량은 원장 사유 문구가 아니라 "검사 수량 − 그 검사가 미검사에서 실제로 뺀 수량"으로 계산합니다.

**시드 데이터**

품목 5종, 검사 항목 품목당 3\~4개, 사용자 7명(역할별 1명 이상 + 403 권한 확인용 역할 없는 계정 `norole` 1명), LOT 30건(검사 전·부분 검사·불합격·출하 완료 섞어서). 시드는 SQL 스크립트와 C# 시더 둘 다 두어 Docker 첫 실행에 자동 적재합니다.

## 7. 검증 계획

코드를 읽지 않고 결과로 확인하는 방식이므로, 검증 장치가 곧 품질 보증입니다. 세 층으로 나누고, 3번 규칙 표의 R1\~R11 각각에 테스트를 짝지어 추적표로 남깁니다.

| 층 | 도구 | 대상 | 완료 기준 |
| --- | --- | --- | --- |
| 단위 | xUnit | 판정 계산, 수량 등식, 해시·멱등 키 생성 | 규칙 R1·R2·R4·R7 통과 |
| 통합 | xUnit + Testcontainers (실제 SQL Server) | 저장 프로시저, 트리거, 동시 요청, 멱등 재전송 | 규칙 R3·R5·R6·R8·R9·R10 통과, 동시 20요청 후 수량 일치 |
| E2E | Playwright | 로그인 → LOT 등록 → 검사 → 승인 → 출하 → 원장 확인 | 시나리오 3개 통과 (정상, 불합격 재검사, 본인 승인 차단) |
| 독립 대조 | 별도 콘솔 앱 (C#) | 앱 계산 모듈을 쓰지 않고 Ledger 합으로 LotQuantities 재계산 | 전 LOT 불일치 0건 |

**AI가 쓴 코드를 AI가 검증하는 문제를 막는 방법**

- 테스트 작성과 구현을 Claude Code의 별도 세션으로 분리합니다. 구현 세션에는 테스트 코드를 보여주지 않고, 테스트 세션에는 구현 코드를 보여주지 않습니다.
- 독립 대조 앱(`tools/Reconcile`)은 앱의 계산 코드·EF 모델·DB 뷰를 참조하지 않고, 원본 테이블 행을 한 시점에 읽어 C#으로 다시 셉니다. 검사 항목: 현재 수량 = 원장 합(7개 수량), 생산 원장 = 생산 수량, 음수 없음·출하 + 예약 ≤ 합격, 출하 실적 합 = 출하 수량, 생산 등식 차이 = R9 초과분, 원장 행마다 근거 원본 행(검사·승인·출하 행, LOT)이 있고 수량·방향이 맞음.
- 기획서의 규칙 표가 테스트의 원본입니다. 테스트가 규칙을 바꾸면 기획서를 먼저 고칩니다.

**검증 실행 규칙**

- 빌드, 단위·통합 테스트, Playwright, 독립 대조는 모두 로컬 Docker에서 실행하고 결과를 기록합니다. GitHub Actions CI는 쓰지 않습니다(2026-11-01 사용자 결정).

**문서에 적을 것과 적지 않을 것**

- 적음: 테스트 수, 통과 범위, 독립 대조 결과, 동시 요청 테스트 조건
- 적지 않음: 성능 수치(측정하지 않음), 실제 현장 적용 성과, "숙련" 표현

## 10. 제외 범위와 주의사항

데모가 보여줄 수 있는 것과 없는 것을 처음부터 분리합니다.

**표현 원칙**

- 특정 회사의 실제 공정·품목·검사 기준을 반영한 것처럼 쓰지 않습니다. 모든 데이터는 가상이라고 표기합니다.
- "C# 숙련", "MS-SQL 능숙"이라고 쓰지 않습니다. "AI 에이전트로 .NET·MS-SQL 환경에서 구현하고 테스트·독립 대조로 검증했다"로 씁니다.

**기술 위험**

- Testcontainers로 SQL Server를 띄우면 첫 실행이 느립니다(이미지 1.5GB 이상). 검증은 7장 규칙대로 로컬에서만 합니다.
- Windows가 아닌 환경(Mac M1 등)에서는 SQL Server 2022 이미지가 안 뜰 수 있습니다. 그 경우 `azure-sql-edge` 이미지로 대체하고 README에 적습니다.
- ClosedXML 엑셀 생성은 한글 글꼴 문제가 없지만, PDF 변환은 범위에서 뺍니다.
