# NK 전산관리부 지원용 데모 기획서 · 검사·출하 이력 관리

Oct 30, 2026 · @사장

## 1. 목적과 배경

전산관리부 공고에서 경력기술서가 비워 둔 두 요건, **.NET 개발**과 **MS-SQL**을 실제 동작하는 데모로 메우는 것이 이 프로젝트의 목적입니다. 데모는 WMS Lite에서 검증한 방식(업무 규칙 정의 → AI 구현 → 테스트·독립 대조로 결과 확인)을 .NET·MS-SQL 환경에서 그대로 재현합니다.
기업정보는 부산에 본사를 둔 고압가스 용기·소방 설비·선박 평형수 처리 시스템 제조사입니다. 전산관리부는 고객용 서비스가 아니라 사내 운영 시스템을 다루는 부서로 보이고, 공고의 .NET·MS-SQL은 기존 사내 시스템이 그 환경이라는 신호로 읽힙니다. 그래서 데모 주제도 제조업 사내 운영 시스템으로 잡습니다.

| 공고 요건 | 경력기술서 현재 | 데모로 보여줄 것 |
| --- | --- | --- |
| .NET 개발 가능자 | 없음 | ASP.NET Core 웹 앱 전체 구현 |
| MS-SQL에 능숙한 자 | PostgreSQL만 | MS-SQL 스키마 설계, 저장 프로시저, 인덱스, 마이그레이션 |
| 바이브 코딩 활용 기획·개발 | MELIGO·TPRI | Claude Code 작업 단위와 검증 기록 공개 |
| 웹 기반 운영 시스템 자동화 | CI/CD 구성 | 일일 보고서 자동 생성, 지연 알림 |
| HTML / JavaScript 이해도 | Next.js·React | 프레임워크 없는 HTML·JS 대시보드 1개 |
| UI/UX 설계 | 기획 경력 | 현장 작업자 화면과 관리자 화면 분리 |

데모는 "숙련"의 증거가 아니라 "이 환경에서도 같은 방식으로 운영 가능한 시스템을 만들 수 있다"는 증거로 쓰고, 포트폴리오에도 그렇게 표기합니다.

## 2. 가상 시나리오와 데모 범위

데모 이름은 **QC Trace**, 주제는 **제조 LOT의 검사·출하 이력 관리**입니다. 가상의 압력 용기 제조사가 생산한 LOT을 검사하고, 합격품만 출하 승인하며, 모든 판정과 수량 변경을 이력으로 남깁니다. 엔케이의 실제 공정을 아는 척하지 않도록 품목·공정·검사 항목은 모두 가상 데이터로 만듭니다.

**업무 흐름**

1. 생산 LOT 등록: 품목, 수량, 생산일, 작업반
2. 검사 의뢰: LOT을 검사 대기로 전환
3. 검사 실적 입력: 항목별 측정값, 합격·불합격·보류 판정, 부분 검사 가능
4. 불합격 처리: 재검사 요청 또는 폐기, 사유 필수
5. 출하 승인: 검사자 본인은 승인 불가, 다른 승인권자가 처리
6. 출하 실적: 출하 수량 확정, 재고 차감, 이력 확정

**포함 범위**

- 기준정보: 품목, 검사 항목(규격·허용 오차), 사용자·역할
- LOT·검사·출하 업무 화면
- 이력 원장: 수량 변경과 판정 변경을 지우지 않고 추가 기록
- 운영 대시보드: 검사 대기 건수, 지연 LOT, 불합격률, 당일 출하
- 자동화: 일일 검사·출하 보고서 자동 생성(엑셀), 검사 지연 LOT 알림
- 관리자 기능: 사용자·역할 관리, 기준정보 CSV 업로드

**제외 범위**

- 실제 계측 장비 연동, 바코드 스캐너 연동
- ERP·MES 연계
- 다국어, 모바일 앱
- 인증 서버 분리(세션 기반 로그인만)

## 3. 핵심 업무 규칙

규칙은 모두 서버에서 검사합니다. 화면에서 막아도 API로 직접 호출하면 같은 결과가 나와야 하고, 각 규칙은 테스트 1개 이상과 짝을 이룹니다.

| 번호 | 규칙 | 이유 | 검증 방법 |
| --- | --- | --- | --- |
| R1 | 검사 완료 전 LOT은 출하 가능 수량에 포함하지 않는다 | 검사 대기 물량을 출하하면 안 됨 | 검사 전 출하 요청 → 거절 |
| R2 | 부분 검사를 허용하고, 합격·불합격·보류·미검사 수량을 각각 유지한다 | 한 LOT을 여러 번에 나눠 검사하는 현장 | 100개 중 60개 검사 후 수량 합이 100인지 |
| R3 | 판정과 수량 변경은 덮어쓰지 않고 이력에 추가한다 | 품질 이력 추적 | 정정 후 원 기록이 남아 있는지 |
| R4 | 불합격 처리는 사유가 없으면 저장하지 않는다 | 원인 분석 근거 | 사유 없는 요청 → 거절 |
| R5 | 검사자 본인은 자기 LOT의 출하를 승인할 수 없다 | 독립 승인 | 본인 승인 요청 → 거절, 타인 승인 → 성공 |
| R6 | 같은 요청 키로 재전송된 실적은 한 번만 반영한다 | 네트워크 끊김 후 재시도 | 같은 키 2회 전송 → 수량 1회 반영 |
| R7 | 출하 수량은 승인된 합격 수량을 넘을 수 없다 | 재고 음수 방지 | 초과 출하 요청 → 거절 |
| R8 | 동시 요청은 LOT 단위로 직렬화한다 | 동시 입력으로 인한 수량 오류 방지 | 동시 요청 테스트, 최종 수량 일치 |
| R9 | 생산 수량보다 많이 검사 등록된 경우 초과분은 보류로 기록하고 삭제하지 않는다 | 실물 보존 | 과입력 요청 → 보류 수량 생성 |
| R10 | 모든 기록에 작업자·시각·사유를 남긴다 | 감사 추적 | 원장 조회에 세 항목이 모두 있는지 |

**수량 지표** (LOT 단위)

- 생산 수량 = 미검사 + 합격 + 불합격 + 보류
- 출하 가능 = 합격 − 출하 완료 − 출하 예약
- 이 등식이 깨지면 대사 화면에 불일치로 표시합니다.

## 4. 화면 구성

현장 작업자 화면과 관리자 화면을 분리합니다. 작업자 화면은 지금 할 일과 남은 수량을 먼저 보여주고, 관리자 화면은 지연과 불일치를 먼저 보여줍니다.

| 화면 | 사용자 | 핵심 요소 | 구현 방식 |
| --- | --- | --- | --- |
| 로그인 | 전체 | 아이디·비밀번호, 역할별 진입 화면 분기 | Razor Pages |
| 운영 대시보드 | 관리자 | 검사 대기·지연 LOT·불합격률·당일 출하, 조치 목록 | 순수 HTML·JavaScript + fetch API |
| LOT 목록·등록 | 생산 담당 | 품목·수량·생산일 입력, 상태별 필터 | Razor Pages |
| 검사 입력 | 검사자 | 항목별 측정값, 자동 판정, 부분 검사 잔량 표시 | Razor Pages + JS 입력 검증 |
| 불합격 처리 | 검사자 | 재검사·폐기 선택, 사유 필수 | Razor Pages |
| 출하 승인 | 승인권자 | 본인 LOT은 버튼 비활성화 + 안내 문구 | Razor Pages |
| 출하 실적 | 출하 담당 | 승인 수량 내 출하, 초과 시 거절 메시지 | Razor Pages |
| 이력 원장 | 관리자 | LOT·작업자·기간 필터, CSV 내려받기 | Razor Pages |
| 재고 대사 | 관리자 | LOT별 수량 등식 확인, 불일치 강조 | Razor Pages |
| 기준정보 | 관리자 | 품목·검사 항목·사용자 관리, CSV 업로드 | Razor Pages |

대시보드만 프레임워크 없이 만드는 이유는 공고의 "HTML / JavaScript 이해도" 요건을 React 없이 보여주기 위해서입니다. 나머지는 .NET 기본 스택인 Razor Pages로 통일해 유지보수 환경과 맞춥니다.

## 5. 기술 구성

공고 환경에 맞춰 .NET과 MS-SQL을 중심에 두고, 나머지는 가장 보편적인 선택으로 고정합니다. 선택 이유를 포트폴리오에서 한 줄씩 설명할 수 있어야 합니다.

| 계층 | 선택 | 이유 |
| --- | --- | --- |
| 런타임 | .NET 8 LTS, C# | 장기 지원 버전, 사내 시스템 유지보수에 적합 |
| 웹 | ASP.NET Core Razor Pages + Minimal API | 화면과 API를 한 프로젝트에서, 과한 구조 없이 |
| DB | SQL Server 2022 (Docker, Developer Edition) | 공고의 MS-SQL, 로컬에서 무료 실행 |
| DB 접근 | EF Core (조회·CRUD) + 저장 프로시저 (수량 변경) | 수량 변경은 SP 안에서 트랜잭션·잠금 처리, MS-SQL 역량 표시 |
| 마이그레이션 | EF Core Migrations + 수작업 SQL 스크립트 | 스키마 이력 관리 |
| 인증 | ASP.NET Core Identity (쿠키 세션) | 기본 제공, 역할 기반 권한 |
| 프론트 | Razor + 순수 JS, 대시보드는 fetch API | 공고의 HTML/JS 요건 |
| 보고서 | ClosedXML로 엑셀 생성, Hosted Service로 매일 실행 | 운영 자동화 요건 |
| 테스트 | xUnit (단위·통합), Testcontainers (실제 SQL Server), Playwright (E2E) | 결과 검증 |
| CI | GitHub Actions | 자동 검증, 실패 시 로컬 검증으로 전환 |
| 배포 | Docker Compose (앱 + SQL Server) | 한 명령으로 재현 |

**MS-SQL에서 보여줄 것**

- 저장 프로시저 `usp_ApplyInspection`, `usp_ApproveShipment`, `usp_ShipLot`: 트랜잭션, `UPDLOCK` 행 잠금, 멱등 키 검사
- 유니크 제약 `(RequestKey)`로 중복 반영 차단
- 원장 테이블은 INSERT만 허용, UPDATE·DELETE 트리거로 거부
- 조회 인덱스: LOT 상태별, 기간별 원장 조회
- 일일 집계 뷰 `vw_DailyQcSummary`

**멱등 처리 방식**

요청 키 + 요청 본문 해시를 `QcRequests` 테이블에 저장합니다. 같은 키가 오면 저장된 결과를 돌려주고, 키는 같은데 본문이 다르면 충돌로 거절합니다. WMS Lite의 `executeWorkflowInTransaction`과 같은 구조를 MS-SQL 저장 프로시저로 옮기는 것이 목표입니다.

## 6. 데이터 모델

테이블 9개로 시작합니다. 현재 상태를 담는 테이블과 이력만 쌓는 테이블을 분리하고, 수량은 항상 이력에서 다시 계산할 수 있어야 합니다.

| 테이블 | 역할 | 주요 열 |
| --- | --- | --- |
| Items | 품목 기준정보 | ItemCode, Name, Spec, IsActive |
| InspectionItems | 품목별 검사 항목 | ItemId, Name, Lower, Upper, Unit |
| Users / Roles | 사용자·역할 (Identity) | UserName, Role (생산·검사·승인·출하·관리자) |
| Lots | 생산 LOT 현재 상태 | LotNo, ItemId, ProducedQty, Status, InspectionRequestedAt, RowVersion |
| LotQuantities | LOT별 수량 지표 | LotId, Uninspected, Passed, Failed, Held, Shipped, Reserved |
| Inspections | 검사 실적 (추가만) | LotId, InspectorId, Qty, Verdict, MeasuredJson, Reason, CorrectsInspectionId, CreatedAt |
| ShipmentApprovals | 출하 승인 (추가만) | LotId, ApproverId, ApprovedQty, Decision, Reason, CreatedAt |
| Shipments | 출하 실적 (추가만) | LotId, ShipperId, Qty, Destination, CreatedAt |
| Ledger | 불변 원장 | LotId, Kind, DeltaField, Delta, ActorId, Reason, SourceTable, SourceId, CreatedAt |
| QcRequests | 멱등 요청 저장 | RequestKey (unique), Operation, BodyHash, ResponseJson, CreatedAt |

**설계 원칙**

- `LotQuantities`는 빠른 조회용이고, `Ledger`의 합과 항상 일치해야 합니다. 대사 화면은 이 둘을 비교합니다.
- `Inspections`·`ShipmentApprovals`·`Shipments`·`Ledger`는 UPDATE·DELETE를 트리거로 거부합니다. 정정은 새 행 + 원 행 참조로 기록합니다.
- `Lots.RowVersion`으로 낙관적 잠금, 저장 프로시저 안에서는 `UPDLOCK`으로 LOT 행 잠금을 겹쳐 씁니다.
- 시각은 UTC로 저장하고 화면에서 한국 시간으로 표시합니다.
- `Lots.InspectionRequestedAt`은 검사 의뢰 시각입니다. 검사 지연(48시간 초과) 판단의 기준입니다.
- `Inspections.CorrectsInspectionId`는 정정 행이 가리키는 원래 검사 행입니다. 원 행은 그대로 남습니다.
- `QcRequests.Operation`은 요청 종류(검사·승인·출하)입니다. 같은 키가 다른 작업에 쓰였는지 구분합니다.
- 출하 승인은 `Reserved`(출하 예약)를 늘리고, 출하는 `Reserved`를 줄인 만큼 `Shipped`를 늘립니다. 그래서 출하 가능 = 합격 − 출하 완료 − 출하 예약이 승인 전후 모두 성립합니다.

**시드 데이터**

품목 5종, 검사 항목 품목당 3\~4개, 사용자 6명(역할별 1명 이상), LOT 30건(검사 전·부분 검사·불합격·출하 완료 섞어서). 시드는 SQL 스크립트와 C# 시더 둘 다 두어 Docker 첫 실행에 자동 적재합니다.

## 7. 검증 계획

코드를 읽지 않고 결과로 확인하는 방식이므로, 검증 장치가 곧 품질 보증입니다. 세 층으로 나누고, 3번 규칙 표의 R1\~R10 각각에 테스트를 짝지어 추적표로 남깁니다.

| 층 | 도구 | 대상 | 완료 기준 |
| --- | --- | --- | --- |
| 단위 | xUnit | 판정 계산, 수량 등식, 해시·멱등 키 생성 | 규칙 R1·R2·R4·R7 통과 |
| 통합 | xUnit + Testcontainers (실제 SQL Server) | 저장 프로시저, 트리거, 동시 요청, 멱등 재전송 | 규칙 R3·R5·R6·R8·R9·R10 통과, 동시 20요청 후 수량 일치 |
| E2E | Playwright | 로그인 → LOT 등록 → 검사 → 승인 → 출하 → 원장 확인 | 시나리오 3개 통과 (정상, 불합격 재검사, 본인 승인 차단) |
| 독립 대조 | 별도 콘솔 앱 (C#) | 앱 계산 모듈을 쓰지 않고 Ledger 합으로 LotQuantities 재계산 | 전 LOT 불일치 0건 |

**AI가 쓴 코드를 AI가 검증하는 문제를 막는 방법**

- 테스트 작성과 구현을 Claude Code의 별도 세션으로 분리합니다. 구현 세션에는 테스트 코드를 보여주지 않고, 테스트 세션에는 구현 코드를 보여주지 않습니다.
- 독립 대조 앱은 앱의 계산 코드를 참조하지 않고 SQL로 직접 집계합니다.
- 기획서의 규칙 표가 테스트의 원본입니다. 테스트가 규칙을 바꾸면 기획서를 먼저 고칩니다.

**CI 운영 규칙**

- GitHub Actions에서 빌드, 단위·통합 테스트, Playwright를 실행합니다.
- Actions가 환경 문제(SQL Server 컨테이너 시작 실패 등)로 반복 실패하면 로컬 Docker에서 같은 명령을 실행해 결과를 기록하고, 원인은 별도 이슈로 남깁니다. CI 복구에 시간을 쓰지 않습니다.

**포트폴리오에 적을 것과 적지 않을 것**

- 적음: 테스트 수, 통과 범위, 독립 대조 결과, 동시 요청 테스트 조건
- 적지 않음: 성능 수치(측정하지 않음), 실제 현장 적용 성과, "숙련" 표현

## 8. Claude Code 작업 단위와 일정

4일, 작업 단위 10개입니다. 각 단위는 Claude Code 세션 하나로 끝나는 크기이고, 끝낼 때마다 테스트가 통과해야 다음으로 넘어갑니다. 아래 표의 지시 요약을 그대로 Claude Code에 붙여 넣어 시작할 수 있게 썼습니다.

| 순서 | 작업 단위 | Claude Code 지시 요약 | 완료 조건 | 일차 |
| --- | --- | --- | --- | --- |
| 1 | 프로젝트 뼈대 | .NET 8 Razor Pages + Minimal API 솔루션, Docker Compose로 SQL Server 2022 포함, 헬스체크 엔드포인트 | `docker compose up` 후 /health 200 | 1 |
| 2 | 스키마·마이그레이션 | 6장 테이블 전부, 원장 테이블 UPDATE·DELETE 거부 트리거, 시드 스크립트 | 마이그레이션 적용, 시드 30 LOT 적재 | 1 |
| 3 | 인증·역할 | Identity 쿠키 로그인, 역할 5개, 역할별 페이지 접근 제한 | 역할 없는 사용자 접근 403 | 1 |
| 4 | 저장 프로시저 3개 | usp\_ApplyInspection, usp\_ApproveShipment, usp\_ShipLot: 트랜잭션, UPDLOCK, QcRequests 멱등 검사, Ledger 기록 | SP 단위 통합 테스트 통과 | 2 |
| 5 | 규칙 테스트 (별도 세션) | 3장 규칙 R1\~R10 테스트를 구현 코드 없이 작성, Testcontainers 사용 | 테스트 파일 존재, 일부 실패 허용 | 2 |
| 6 | 업무 화면 | LOT 등록, 검사 입력, 불합격 처리, 출하 승인, 출하 실적 Razor Pages | R1\~R10 테스트 전부 통과 | 2\~3 |
| 7 | 원장·대사·기준정보 | 원장 필터 조회, CSV 내려받기, 대사 화면, 기준정보 CSV 업로드 | 대사 불일치 0건 표시 | 3 |

| 9 | 자동화 | Hosted Service로 매일 08:00 엑셀 보고서 생성, 검사 지연 LOT(48시간 초과) 알림 목록 | 보고서 파일 생성 확인 | 4 |

**세션 운영 규칙**

- 세션 시작 시 이 기획서의 해당 장(규칙 표, 데이터 모델)을 붙여 넣습니다. 구현 세션에는 7장 검증 계획의 테스트 코드를 보여주지 않습니다.
- 세션 끝에 `dotnet test` 결과와 변경 파일 목록을 받아 기록합니다.
- git commit은 사장님 확인 후에만 합니다.
- 4일 안에 못 끝내면 9번(자동화)과 8번(대시보드) 순서로 뺍니다. 1\~7번은 빼지 않습니다.

## 10. 제외 범위와 주의사항

데모가 보여줄 수 있는 것과 없는 것을 처음부터 분리합니다. 면접에서 가장 먼저 나올 질문도 여기에 있습니다.

**표현 원칙**

- 엔케이의 실제 공정·품목·검사 기준을 아는 것처럼 쓰지 않습니다. 모든 데이터는 가상이라고 매 장에 표기합니다.
- "C# 숙련", "MS-SQL 능숙"이라고 쓰지 않습니다. "AI 에이전트로 .NET·MS-SQL 환경에서 구현하고 테스트·독립 대조로 검증했다"로 씁니다.
- 테스트 수는 자동화 실행 건수라고 밝히고, 성능 수치는 측정하지 않았으면 적지 않습니다.

**면접 대비**

- "저장 프로시저를 직접 짤 수 있나요?" → 직접 작성하지는 않지만 4장 발췌 코드의 동작(잠금, 멱등 키, 트랜잭션)은 설명할 수 있어야 합니다. 10번 작업 단위 끝에 설명 연습을 포함합니다.
- "AI 없이 유지보수가 되나요?" → AI 사용 가능 여부를 먼저 묻고, 불가하면 이 역할은 맞지 않다고 솔직하게 답합니다.
- "왜 Razor Pages인가요?" → .NET 기본 스택이고, 사내 시스템 유지보수에 가장 흔한 선택이라서입니다.

**기술 위험**

- Testcontainers로 SQL Server를 띄우면 첫 실행이 느립니다(이미지 1.5GB 이상). CI에서 반복 실패하면 7장 규칙대로 로컬 검증으로 전환합니다.
- Windows가 아닌 환경(Mac M1 등)에서는 SQL Server 2022 이미지가 안 뜰 수 있습니다. 그 경우 `azure-sql-edge` 이미지로 대체하고 README에 적습니다.
- ClosedXML 엑셀 생성은 한글 글꼴 문제가 없지만, PDF 변환은 범위에서 뺍니다.
